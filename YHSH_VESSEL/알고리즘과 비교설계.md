# 알고리즘과 비교설계

논문 그림 Fig1~Fig8 뒤에 무엇이 돌아갔는지 정리한 문서. 저장소
`DragonTrainerTristana/DT_Vessel` 의 여섯 브랜치(`msgComparision` `main` `Thick_MoE`
`Light_MoE` `Shared_MoE` `A_star`)와 `archive/*` 다섯 개를 전부 읽고 확인한 내용임.

어느 그림이 어느 *실행*에서 나왔는지는 **그래프 매칭 정리.txt** 를 볼 것. 이 문서는
그 실행들이 *무엇을 어떻게* 학습하고 비교했는지를 다룸.

## 1. 전체 구성

원본 시뮬레이터는 Unity ML-Agents(C#)이고 정책 학습은 Python임. git root 가
`Assets/Scripts/` 라서 저장소 최상위에 C# 과 `Python/` 이 나란히 있음.

논문 실험은 Unity 가 아니라 **`vessel_gym.py`** 에서 돌았음. Unity ↔ Python 동기 왕복이
초당 25스텝에서 막혀서, C# 원본(`VesselDynamics` `VesselRadar` `COLREGsHandler`
`VesselManager`)의 수식을 그대로 옮긴 GPU 배치 시뮬레이터를 만들어 수천 환경을 동시에
굴렸음. 정책망(`networks.py`)과 체크포인트는 양쪽이 공유하므로 학습된 정책을 그대로
Unity 로 되가져갈 수 있음.

| 층 | 파일 | 역할 |
|---|---|---|
| 시뮬레이터 (원본) | `Agent/` `Navigation/` `Management/` (C#) | 동역학 · 레이더 · COLREGs 판정 · 보상 |
| 시뮬레이터 (배치) | `Python/vessel_gym.py` | 위 수식의 GPU 이식. `[E, N]` 텐서 (환경 × 선박) |
| 정책망 | `Python/networks.py` | 세 망 + MoE + 통신. Unity·배치 공용 |
| 학습 | `Python/vessel_gym_train.py` | PPO 루프 |
| 평가 | `eval_ckpt.py` `eval_mixed.py` `astar_fig9/eval_astar_global.py` | 정책 고정 후 재측정 |

**스케일**: 원본 치수에 `VESSEL_SCALE=0.2` 를 곱해 씀. 레이더 280→**56m**,
통신 2100→**420m**. 0.3 배는 충돌률 78%로 학습이 안 됐고 0.1 배는 충돌이 0이라,
학습 가능한 구간을 찾아 정한 값임. 물리 스텝 `dt=0.04s`, 결정 하나당 10 서브스텝(0.4초).

## 2. 관측과 행동

관측 369D. 이 중 네트워크에 들어가는 건 366D임.

| 슬롯 | 크기 | 내용 |
|---|---|---|
| radar | 360 | 360방향 raw ray 거리. 프레임 3장 쌓음 |
| goal | 2 | 목적지 거리 `d/(d+150)` · 방위 `/180` |
| self | 4 | 속력 · 선회율 · 침로 · 타각 |
| position | 2 | 통신 범위 계산 전용 (**학습 입력 아님**) |
| situation | 1 | COLREGs 상황 0~4. MoE 라우팅 + one-hot 입력 |

행동은 연속 2D — **타각(rudder)** 과 **추력(thrust)**. Squashed Gaussian 을 씀:
정규분포에서 뽑고 `tanh` 로 [-1,1] 에 눌러 담은 뒤 log-prob 을 보정함. 표준편차는
학습 파라미터이고 차원별로 다르게 초기화함(타각 `std≈0.37`, 추력 `std≈0.61`).

과거에 있던 ARPA 21D 슬롯은 제거됐음. 충돌 기하는 360 raw ray 와 프레임 스택으로
대체함 — 아래 RadarEncoder 항목 참고. COLREGs one-hot 도 관측에서 뺐다가
(vessel-label 누출) 별도 경로로 다시 넣었음.

## 3. 학습 알고리즘 — PPO

CleanRL 구현 방식을 따름. 하이퍼파라미터는 `config.py` 에 있음.

| 항목 | 값 |
|---|---|
| 할인율 γ | 0.99 |
| GAE λ | 0.95 |
| clip ε | 0.2 |
| 학습률 | 3e-4 (Adam) |
| rollout | 2048 |
| minibatch | 512 |
| epoch | 2 |
| 엔트로피 보너스 | 0.01 |
| value 손실 가중 | 0.5 |
| gradient clip | 0.5 |

Advantage 는 배치 단위로 정규화함. `action_raw`(tanh 이전 샘플)를 메모리에 저장해
업데이트가 그대로 재사용하므로, epoch 0 에서 PPO ratio 가 포화 샘플까지 정확히 1.0 이
됨. 이건 tanh 정책에서 흔한 오차 원인을 막는 조치임.

## 4. 신경망

망이 셋임. 각자 자기 레이더 인코더를 가짐.

| 망 | 입력 | 출력 |
|---|---|---|
| MessageActor | 관측 | 메시지 `msg_dim`(기본 6) — `tanh` |
| ControlActor | 관측 + 게이트·이웃메시지 | 행동 2D |
| Critic | 관측 + 게이트·이웃메시지 | 가치 |

`fc2` 입력의 concat 순서는 **항상** `[radar, goal, self, (situation one-hot), msg]` 임.
메시지가 맨 뒤여야 `[:, -msg_dim:]` 로 메시지 슬라이스를 인덱싱하는 초기화·계측 코드가
성립함.

### RadarEncoder — 이 연구의 핵심 기법 중 하나

360개 raw ray 를 **학습형으로** 30D 까지 압축함. Conv1D 세 겹 + FC 구조임.

- **프레임을 입력 채널로 씀.** 입력이 `[M, frames=3, rays=360]` 이라, 같은 ray 칸의
  프레임 간 변화 — 즉 **방위 변화율(bearing rate)** — 을 conv 가 직접 봄. 이게
  COLREGs 판단의 핵심 신호라서, ARPA 를 손으로 계산해 넣던 걸 대체할 수 있었음.
- **원형 패딩(`padding_mode='circular'`).** ray 359 와 ray 0 이 각도상 이웃이므로
  wrap 을 존중함. 정면을 가로지르는 물체가 경계에서 잘리지 않음.
- **stride 2 세 번**으로 360→180→90→45 다운샘플. 고정 min-pool 이 아니라 학습형임.

원래 C# 쪽에서 360 ray 를 30 섹터로 min-pool 해서 보냈는데, 고정 압축이라 정보가
버려졌음. 그걸 걷어내고 같은 30D 로 압축하되 **무엇을 남길지를 학습이 정하도록** 바꾼 것.

이 인코더가 신경망 파라미터의 **89%** 를 차지함 (369,131 중 328,794). 아래 MoE 이야기가
전부 여기서 나옴.

### MoE 네 종류 — Fig2 의 비교 축

COLREGs 상황 5개(없음 / 정면 / 교차유지 / 교차양보 / 추월)로 **hard-route** 함.
어디로 보낼지를 학습하지 않고 선박 간 기하로 판정해 바로 꽂음. 그래서 흔한
전문가 붕괴(한 전문가로 쏠려 나머지가 죽는 것)가 구조적으로 없음.

네 구조의 차이는 이 5갈래를 **어디까지** 적용하냐임.

| 구조 | 설정 | 인식부 | 판단부 | 파라미터 |
|---|---|---|---|---|
| 단일망 | `USE_MOE=0` | 1벌 | 1벌 | 369,131 |
| 분리·얇게 | `USE_MOE=1 MOE_WIDTH=0.44` | 5벌(얇게) | 5벌 | 363,004 |
| 분리·두껍게 | `USE_MOE=1 MOE_WIDTH=1.0` | 5벌 | 5벌 | 1,826,719 |
| **공유 (제안)** | 위 + `MOE_SHARED=1` | **1벌** | 5벌 | **511,543** |

무거운 레이더 인식부를 5벌 복제하니 1.83M 으로 뛰는 것이고, 제안 구조는 그걸 한 벌만
두고 판단부만 5벌로 두어 512K 에 그침. 늘어난 건 40,337 → 182,749 뿐임.

**분리·얇게(363K)의 존재 이유**는 등파라미터 대조임. 단일망(369K)과 파라미터가 거의
같으므로, 여기서 성능 차가 나면 그건 *용량* 이 아니라 *상황별 전문화* 효과임.
용량 효과와 전문화 효과를 분리하려고 둔 조건임.

구현 두 가지:
- `_share_radar_encoder()` — 전문가들의 `radar_encoder` 를 `experts[0]` 것으로 통일.
  옵티마이저가 공유 텐서를 자동 dedup 하고, `state_dict` 는 5벌 동일 사본으로 저장해
  로드 호환을 유지함.
- `_w(n, width)` — 폭 스케일은 **코어 내부 차원에만** 적용함. 메시지 6D, 행동 2D,
  goal/self 입력 같은 외부 인터페이스는 건드리지 않음. `width=1.0` 이면 기존 구조와
  비트 동일.

## 5. 통신

**설계 의도**: 통신 거리(420m)를 레이더(56m)보다 훨씬 크게 잡았음. 그래야 부분관측이
생기고, 먼 배의 정보는 통신으로만 알 수 있어서 통신이 *필요해짐*. 완전관측이면
통신은 잉여가 되어 아무 차이도 안 남.

메시지는 `MAX_COMM_PARTNERS`(기본 4)명의 가장 가까운 이웃에게서 받음.

### 집계 방식 — Fig3 의 비교 축

| 방식 | 환경변수 | 계산 |
|---|---|---|
| sum / mean / scale | `VESSEL_AGG_MODE` | 단순 합 · 평균 · 개수 스케일 |
| **위치 grounding + 평균** | `POS_GROUND=1` | `[상대방위·거리 ⊕ 메시지]` → encoder → 평균 |
| attention | `USE_ATTENTION=1` | 아래 |

**논문 그림의 기본 설정은 `POS_GROUND=1`, `USE_ATTENTION=0`** — 위치를 붙인 뒤 마스크
평균임. attention 은 구현돼 있으나 이번 그림에는 쓰지 않았음.

`GroundedAttention` 은 single-head(내부 차원 32)임. query 는 **수신자**의
`[self ⊕ goal]`(내 상황), key/value 는 각 파트너의 `[상대위치(sin,cos,거리) ⊕ 메시지]`
(어디서 온 어떤 의도). 즉 "내 상황에 비추어 누구 말을 들을지"를 가중선택함.

### 게이트 — 공정성 장치

`others_msg * sigmoid(msg_gate)` 로 곱함. `msg_gate` 는 학습되는 스칼라이고 초기값 0
(= sigmoid 0.5, 중립)임. **정책이 메시지를 무시할 수 있다**는 게 요점임. 그래서
"통신 ON 이 OFF 보다 나쁠 수 없다"(정보의 가치 ≥ 0)가 구조적으로 보장됨. 이게 깨지면
구현 버그로 판정함.

### 두 개의 함정과 그 처리

이 부분은 논문에 쓸 만한 실측 근거가 있음.

**(1) zero-init 채널 동결.** 메시지 경로를 0 으로 초기화하면 생산측 0 과 소비측 0 이
직렬로 곱해지는 안장점이 생겨서 **양쪽 gradient 가 항등 0** 이 됨. 체크포인트를 열어
확인한 결과 100만 스텝 동안 비트 단위로 얼어 있었음. 그래서 zero-init 대신 **×0.1
소진폭 초기화**를 씀 — gradient 는 1스텝부터 살아 있고 초기 영향만 작음.
`fc2` 메시지 슬라이스와 `v_proj` 양쪽에 적용함.

**(2) sender → receiver gradient 누락.** PPO 배치가 `n_agent=1` 이라 예전
`evaluate_actions` 는 자기 자신 루프만 타서, "내 메시지가 옆 배를 도왔나"라는
gradient 가 **0** 이었음. 즉 통신이 학습되지 않고 있었음. 지금은 파트너의 관측을
메모리에 저장해 두고, 업데이트 때 MessageActor 를 파트너 관측으로 재실행함.
rollout 과 업데이트가 **같은 집계 함수**를 쓰도록 맞춰야 PPO ratio 가 유효하므로,
sum·mean·pos_ground·attention 각 경로를 양쪽에서 미러링함.

### 보조 손실 다섯 가지

메시지가 실제로 쓸모 있는 내용을 담도록 강제하는 self-supervised head 들임. **전부
정책·가치 경로와 분리된 별도 head** 라서, 손실이 MessageActor 로만 흐르고 수신측
정책은 오염되지 않음 (= 게이트로 메시지를 무시할 자유가 보존됨).

| head | 메시지가 무엇을 담게 하나 | 계수 |
|---|---|---|
| IntentDecoder | 송신자의 K스텝 미래 의도 (상대변위 + 침로변화) | `INTENT_COEF` |
| **ThreatDecoder** | 송신자가 본 최근접 위협 K개의 기하 (방위·거리·접근율) | `THREAT_COEF` |
| GoalDecoder | 송신자의 목적지 | `GOAL_COMM_COEF` |
| RoleDecoder | 송신자의 COLREGs 역할 (교차 분류) | `ROLE_COMM_COEF` |
| consumer_decoder | *수신측* 표상에서 파트너 목적지 복원 | `COMM_CONSUMER_COEF` |

**논문 그림의 설정은 `THREAT_COEF=0.5` 하나만 켠 상태임.** 나머지는 0.

ThreatDecoder 를 고른 이유가 설계의 핵심임 — 가림(occlusion)으로 수신자가 못 보는
제3의 위협을 메시지로 복원하게 만들면, 통신이 *없으면 안 되는* 상황이 실제로 생김.
GoalDecoder 도 같은 논리(통신 420m > 레이더 56m)지만 이번엔 쓰지 않았음.

`consumer_decoder` 만 성격이 다름. 나머지 넷은 **생산자**만 학습시켜서 수신 쪽이
끊긴 채로 남는 문제가 있었는데, 이건 수신 정책이 파트너 의도를 표상하도록 **수신측에
gradient** 를 주는 것임.

## 6. COLREGs

### 상황 판정 — `Navigation/COLREGsHandler.cs`

선박 간 기하로 5분류함. 순서대로 걸러냄:

1. 감지 거리 밖 → **None**
2. `|방위| > 100°` (내 뒤쪽) → **None**
3. 좌현 대 좌현(양쪽 다 −10° 미만) 또는 우현 대 우현(양쪽 다 10° 초과) → **None** — 안전 통과 중
4. TCPA 계산 → 멀어지는 중이면 **None**
5. 양쪽 `|방위| < 15°` → **HeadOn**
6. 상대 기준 `|방위| > 112.5°` (내가 상대 뒤) → **Overtaking**
7. `|방위| < 112.5°` → 방위 > 0 이면 **CrossingGiveWay**, < 0 이면 **CrossingStandOn**

Rule 8·17 의 시간·거리 임계(조기 조치, 실질 조치, 17(b)·17(c), 안전 통과 거리,
임계 CPA)도 상수로 들어 있고 전부 `GlobalScale` 을 통해 스케일에 비례함.

7번 항목의 `> 5°` 하한은 2026-07-03 에 제거됐음. HeadOn(상호 15° 필요)도 Crossing 도
아닌 각도대가 None 으로 새는 사각지대를 만들고 있었음.

### 보상 — Fig5 의 비교 축

보상은 12항이 넘음. 주요 항목:

| 항 | 값 | 목적 |
|---|---|---|
| 도착 | +100 | |
| 충돌 | **−300** | 회피 압력. 분류 임계 −150 과 짝 |
| 목적지 접근 | ×1.0 | progress shaping |
| 목적지 방향 | ×0.15 × 속력비 | 0.5 → 0.15 로 낮춤 (돌진이 회피를 이기던 문제) |
| 시간 | −0.07/스텝 | −0.1 → −0.07 (우회 비용 완화) |
| 저속 | −0.15 | 단, **충돌코스면 ×0.3 로 감면** |
| 연료 | −0.02 × (추력² + 0.5·선회²) | 멀리서 부드럽게 회피하도록 |
| 근접 | −2.0 | 돌진 보상(+1.3)을 확실히 이기게 |
| 충돌코스 | −0.8 × 위험도 | |
| **조기 회피** | **+0.3** | 멀리서 DCPA 를 벌릴 때 |
| 타각 평활 | −0.02 | 급변침 억제 (연료 논제) |
| 명령-실제 불일치 | −0.03 | 타속 한계에 박는 정도 |
| **COLREGs 준수** | **× 0.45 × 위험가중** | **Fig5 가 켜고 끄는 항** |

보상 설계에서 반복해 잡은 문제가 **"돌진이 회피를 지배(strictly dominated)"** 하는
현상임. 저속 패널티가 충돌코스에서의 감속까지 벌하고, 방향·직진·시간 항이 경로에
의존해 돌진에 유리하게 쌓였음. 저속 패널티 감면(Rule 8 속도 회피 언락), 방향 계수
인하, 조기 회피 보상 추가가 그에 대한 대응임.

## 8. 평가 프로토콜

**막대 그림의 값은 학습 로그가 아님.** 학습이 끝난 뒤 정책을 고정하고 다시 항해시켜
잰 값임. 학습 중 로그는 에피소드가 한꺼번에 끝나는 타이밍 때문에 창마다 심하게
흔들려서 최종 성능 판단에 쓸 수 없음.

```
python eval_ckpt.py --ckpt <ckpt> --arm ON --max_partners 4 \
       --envs 96 --burnin 1500 --eval_decisions 3500
```

`--burnin` 은 집계하지 않고 먼저 돌리는 구간임. 전부 같은 시점에 출발하면 종료도
몰려서 통계가 깨지므로, 위상을 흩뜨린 다음부터 셈.

측정 지표: 도착·충돌·시간초과 비율, 연료, 침로 변화 총량, 소요 시간, 최소 선박간
거리, COLREGs 준수율(전체 및 상황별).

**Fig7 은 다른 하네스**(`eval_mixed.py`)를 씀. 비율 7가지를 환경마다 다르게 심어
한 번에 재는 구조라 7번 따로 도는 것보다 빠르고 burn-in 도 한 번만 냄.
`--mode radar` 는 송수신 모두 차단, `--mode rx` 는 수신만 허용(= 통통배).
**최종 그림에 쓴 건 `rx` 하나임.**

**곡선과 막대는 다른 자로 잰 값이라 숫자를 직접 비교하면 안 됨.**

### 학습곡선의 세로축

로그에 찍히는 `R` 이 아님. 같은 로그의 결과 분포로 다시 계산한 값임.

```
보상 = 1.5 × 도착 − 6.0 × 충돌 − 0.5 × 시간초과      (창별 종료 에피소드 수로 가중)
```

로그 `R` 은 매 결정마다 주는 유도 보상의 평균이라 도착·충돌 같은 최종 결과와 상관이
거의 없음(실측 r ≈ 0.02). 그대로 그리면 곡선과 성능 그림이 딴소리를 함. 위 식은 전
조건에 똑같이 적용했고, 충돌 가중치를 3배에서 15배까지 바꿔도 조건 간 순서는 안 바뀜.

## 9. 비교 설계의 원칙

이 연구가 일관되게 지킨 규칙들임. 논문 방법론 절에 쓸 수 있는 내용.

**한 축에 변수 하나.** 각 그림은 자기가 건드리는 값 하나만 바꾸고 나머지는 전부
고정임. Fig3 은 `--max_partners` 만, Fig4 는 `VESSEL_MSG_DIM` 만, Fig6 은
`--comm_on_at` 만 다름. 공통 설정은 전 실행 동일:

```
--envs 128 --vessels 16 --rollout 32 --steps 16000000 --ring 0.7
--comm_on_at 9000000        VESSEL_MSG_DIM=6         VESSEL_RADAR_RANGE=56
--max_partners 4            VESSEL_THREAT_COEF=0.5   VESSEL_SIM_COLREGS_COEF=0.45
VESSEL_POS_GROUND=1         VESSEL_USE_ATTENTION=0
```

**불구화된 기준선을 이기는 건 무효 (anti-rigging).** 문서에 반복해 등장하는 원칙임.
구체적으로:
- `USE_MOE=0` 이 단일망과 **비트 동일**함을 검증해 둠 — MoE 의 이득이 구조 때문인지
  다른 변경 때문인지 헷갈리지 않게.
- 게이트 개방 패널티는 통신 OFF 팔에서 `others_msg ≡ 0` 이라 무영향 → 손실에 더해도
  OFF 학습이 변하지 않음.
- 보조 손실 계수가 0 이면 손실이 비트 동일하게 유지됨.
- 상황 one-hot 입력은 통신 ON/OFF 양쪽에 동일 적용함.

**통신은 나빠질 수 없다는 불변식(H1a).** 게이트로 메시지를 무시할 수 있으므로
comm-ON ≥ comm-OFF 가 성립해야 함. 위배되면 통신의 실패가 아니라 구현·최적화 버그로
간주함. 그 위에서 comm-ON > comm-OFF(H1b)는 과제가 통신을 *필요* 로 할 때만 성립하는
조건부 목표로 둠.

**차원 무차별은 H2 반증이 아님.** 메시지 차원 2~12 가 동일하게 수렴한 전례가 있는데,
그건 차원이 무의미해서가 아니라 통신이 아예 안 쓰이고 있다는 증거였음. 그래서 Fig4 의
해석은 Fig1 에서 통신 효과가 확인된 뒤에만 유효함.
